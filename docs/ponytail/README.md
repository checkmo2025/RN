# Ponytail 고도화·리팩터링 기록

Ponytail로 수행한 개선을 포트폴리오에서 재사용할 수 있도록 가설, 코드 변화, 측정 결과와
결론을 기능 단위로 남긴다. 측정하지 않은 성능은 개선됐다고 쓰지 않는다.

## 파일 구성

- [`TEMPLATE.md`](./TEMPLATE.md): 새 기록을 만들 때 복사하는 원본
- [`ponytail-news-carousel-2026-08-27-2350.md`](./ponytail-news-carousel-2026-08-27-2350.md): 소식 캐러셀 공통화 시범 기록

기능별 기록 파일은 다음 이름을 사용한다.

```text
ponytail-관련-기능-YYYY-MM-DD-HHmm.md
```

문서 제목은 시간을 읽기 쉽게 표시한다.

```text
# ponytail-관련-기능-YYYY-MM-DD-HH:mm
```

## 작성 원칙

1. 변경 전·후 코드를 적는다. 코드가 길면 판단에 필요한 핵심 부분만 인용하고 실제 파일을 링크한다.
2. 변경 전에 가설, 근거, 기대 결과와 성공 기준을 먼저 정한다.
3. 사용자가 요구한 기능, 데이터, 순서, 문구, 오류 처리와 권한 규칙을 바꾸지 않는다.
4. 측정 조건과 명령을 남기고, 변경 전·후를 같은 조건에서 비교한다.
5. 결과에 따라 가설을 `확인`, `부분 확인`, `기각`, `측정 보류` 중 하나로 판정한다.
6. 기본 작업 범위는 핵심 구현 코드의 추가+삭제 합계 200줄 이내로 한다.
7. 테스트·문서·생성물·잠금 파일의 변경량은 핵심 구현 코드와 분리해 함께 기록한다.
8. 200줄을 넘겨 한 번에 처리하는 편이 효율적이면 예외 사유, 분할하지 않은 이유, 위험과 복구 방법을 적는다.
9. 서로 독립적인 기능은 파일을 나눈다. 같은 원인과 측정 기준을 공유할 때만 한 기록으로 묶는다.

## 권장 측정 지표

모든 지표를 억지로 채우지 않는다. 작업의 가설과 직접 연결된 지표만 선택하고, 해당하지 않으면
`N/A`와 이유를 적는다.

### 항상 기록

| 분류 | 지표 |
| --- | --- |
| 동작 보존 | 결과 ID·개수·순서, 화면 상태, 오류·권한 처리, API 경로·호출 순서 |
| 구조 | 중복 구현 수, 변경 지점 수, 대상 코드 줄 수, 직접 의존성 수 |
| 변경 규모 | 핵심 구현·테스트·문서별 추가/삭제 줄 수, 200줄 예산 사용률 |
| 품질 | 회귀 테스트 통과 수, TypeScript, ESLint, 필요한 E2E·실기기 결과 |

### 성능 가설이 있을 때 기록

| 분류 | 권장 지표 | 측정 기준 |
| --- | --- | --- |
| 응답 | 완료 시간 중앙값·p95 | 동일 기기·빌드·데이터·네트워크에서 워밍업 5회 후 30회 이상 |
| 네트워크 | API 요청 수, 전송 바이트 | 동일 사용자 흐름 1회 기준 |
| 렌더링 | React 렌더 횟수, 긴 프레임·드롭 프레임 | 동일 화면 조작 시나리오 기준 |
| 자원 | JS 메모리, 앱 번들 크기 | 동일 빌드 모드와 측정 도구 사용 |

성능을 건드리지 않는 코드 이동·중복 제거라면 요청 수와 시간복잡도가 그대로인지 확인하고
`성능 개선 없음`으로 결론 내리는 것이 올바른 측정이다.
