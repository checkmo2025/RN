## 2. 변경 전

팔로우 화면이 `ScrollView` 내부에서 배열 전체를 `map()`으로 즉시 React 요소로 만들었다.
목록이 길어지면 현재 화면 밖의 사용자 행도 함께 생성된다.

```tsx
<ScrollView refreshControl={refreshControl}>
  {activeFollowUsers.map((user) => (
    <View key={`${activeFollowTab}-${user.nickname}`} style={styles.followUserRow}>
      {/* 프로필 이동과 구독 상태 변경 */}
    </View>
  ))}
</ScrollView>
```

| --- | ---: | --- |

## 3. 가설·근거·기대 결과

### 가설

팔로우 화면의 `ScrollView`와 `map()`을 React Native의 `FlatList`로 바꾸면 화면 밖 행을
한꺼번에 생성하지 않으므로 긴 목록의 초기 렌더 작업과 메모리 사용을 줄일 수 있다. 같은 데이터,
키와 행 상호작용을 전달하면 사용자 동작은 유지될 것이다.

### 근거

- 기존 `map()`은 `activeFollowUsers`의 모든 항목을 한 번에 React 요소로 변환한다.
- `FlatList`는 보이는 영역 주변의 항목을 창 단위로 렌더링하는 React Native 기본 컴포넌트다.
- 별도 라이브러리와 데이터 변환 없이 기존 배열을 `data`로 전달할 수 있다.
- 마이페이지 팔로우 목록에 같은 구조를 먼저 적용해 TypeScript와 프로덕션 export를 통과했다.

## 7. 가설 판단과 결론

### 판정

`부분 확인`

### 근거

- 전체 배열의 행을 즉시 만드는 `map()`이 1곳에서 0곳으로 줄고 `FlatList`가 1곳 생겼다.
- 기존 `activeFollowUsers`, 닉네임 키, 구독 핸들러와 새로고침 함수를 그대로 연결했다.
- 기존 데이터가 있는 로딩 상태에서도 스켈레톤과 사용자 행을 함께 표시하는 흐름을 유지했다.
- 사용자 프로필 본문의 책 이야기·서재·모임과 해당 `ScrollView`는 변경하지 않았다.
- 19명에서는 첫 커밋 중앙값이 27.19ms에서 22.60ms로 16.9% 줄었다.
- 100·500명에서는 초기 행 생성이 각각 100→50, 500→50으로 제한되고 첫 커밋 중앙값이
  각각 85.2%, 97.1% 줄었다.
- 이번에 확인한 대상 화면의 최대 규모인 7명에서는 첫 커밋 중앙값이 16.20ms에서 19.89ms로 22.8%
  늘었다. 작은 목록에서는 `FlatList` 자체 고정비가 더 컸다.
- 긴 목록의 최악 프레임 간격은 줄었지만 배치 렌더로 20ms 초과 프레임 횟수는 늘었다.

### 결론

다른 사용자 프로필의 팔로워·팔로잉 목록을 React Native 기본 `FlatList`로 바꿔 전체 행 즉시
생성 코드를 1곳에서 제거했다. 데이터, 순서, 프로필 이동, 구독 상태 변경과 새로고침 로직은
그대로 연결했다. 핵심 변경은 172줄로 200줄 예산 안이며 새 의존성은 없다.

가설은 목록 규모에 따라 부분 확인됐다. 확인한 7명 규모에서는 약 3.70ms의 고정비가 생겼지만,
`book_cafe`와 같은 19명 규모부터 초기 커밋 단축이 관찰됐고 100명 이상에서는 모든 행을 한꺼번에
만들지 않는 효과가 뚜렷했다. 따라서 이 변경은 현재 최소 지연만 위한 최적화라기보다 팔로우 수
증가에 대비한 확장성 개선이다. 메모리 개선은 측정하지 않았으므로 주장하지 않는다.

### 후속 작업

실기기에서 실제 화면 진입과 끝까지 스크롤하는 시나리오를 각각 30회 측정한다. Instruments로
메모리와 네이티브 dropped frame을 분리 측정하면 시뮬레이터 미세 벤치마크의 한계를 보완할 수 있다.
