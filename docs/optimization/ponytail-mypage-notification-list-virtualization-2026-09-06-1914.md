## 2. 변경 전

마이페이지 전체가 `ScrollView`이고 `내 알림`은 수집된 모든 행을 `map()`으로 즉시 만들었다.
목록이 길어지면 화면 밖의 알림도 첫 렌더 과정에 포함됐다.

```tsx
<ScrollView contentContainerStyle={styles.scrollContent}>
  <View style={styles.listContainer}>
    {alarms.map((alarm) => (
      <Pressable key={alarm.id} onPress={() => handlePressAlarm(alarm)}>
        {/* 읽음 점, 알림 문구, 상대 시간 */}
      </Pressable>
    ))}
  </View>
</ScrollView>
```

## 3. 가설·근거·기대 결과

### 가설

마이페이지 스크롤 컨테이너와 `alarms.map()`을 React Native 기본 `FlatList`로 바꾸면 화면 밖 행을
한꺼번에 만들지 않으므로 긴 목록의 첫 커밋 시간과 250ms 동안 생성되는 알림 행 수가 감소한다.
기존 배열, 키, 행 UI와 핸들러를 그대로 전달하면 사용자 동작 계약은 유지될 것이다.

### 근거

- 기존 코드는 `alarms.map()` 결과 전체를 `ScrollView` 자식으로 전달했다.
- `FlatList`는 화면 주변 항목을 창 단위로 렌더링하며 React Native에 이미 포함되어 있다.
- 같은 화면의 팔로우와 `내 소식` 목록이 이미 `FlatList` 패턴을 사용한다.
- 데이터 수집, 알림 매핑, 읽음 처리와 화면 이동은 렌더 컨테이너와 독립되어 있다.
- 프로필 헤더와 다른 탭 콘텐츠는 `ListHeaderComponent`에 그대로 두면 중첩 스크롤 없이 유지할 수 있다.

## 4. 변경 후

`alarms`를 데이터로 전달한다. 다른 탭은 기존 콘텐츠를 목록 헤더 안에서 그대로 렌더링한다.

```tsx
<FlatList
  data={isLoggedIn && activeTab === '내 알림' ? alarms : []}
  keyExtractor={(alarm) => alarm.id}
  renderItem={renderAlarmItem}
  ListHeaderComponent={/* 기존 프로필, 버튼, 탭과 다른 탭 콘텐츠 */}
  ListEmptyComponent={
    activeTab === '내 알림' && isLoggedIn ? renderAlarmStatus() : null

  refreshControl={/* 기존 새로고침 처리 */}
/>
```

### 근거

- 모든 알림 행을 즉시 만드는 `alarms.map()`이 1곳에서 0곳으로 줄고 `FlatList`가 1곳 생겼다.
- 기존 `alarms`, ID 키, 표시 순서, 읽음 표시와 `handlePressAlarm()`을 그대로 연결했다.
- 알림 API, 페이지 수집, 읽음 실패 복구, 오류·권한 처리는 수정하지 않았다.
- 19·100·500개에서 첫 커밋 중앙값이 각각 13.5%, 81.5%, 93.5% 줄었다.

- 정적 검사, 실제 Release 빌드와 로그인 시뮬레이터의 오류·빈 상태 및 다른 탭 복귀가 통과했다.

### 결론

마이페이지 `내 알림` 목록을 React Native 기본 `FlatList`로 바꿔 전체 행 즉시 생성 코드를
제거했고 데이터·API·표시 순서·문구·읽음 처리와 이동 로직은 유지했다. 핵심 변경은 146줄로
200줄 예산 안이며 새 의존성은 없다. Release 렌더러 실험에서 19개부터 첫 커밋이 13.5% 단축됐고,
100·500개에서는 각각 81.5%, 93.5% 단축됐다. 7개에서는 25.3% 느려져 가설은 목록 규모에 따라
부분 확인됐으며, 결과는 알림 API와 화면 전환을 제외한 렌더러 마이크로 벤치마크로 한정한다.

### 후속 작업

알림 API가 정상이고 실제 알림이 20개 이상인 계정을 준비할 수 있을 때 실기기에서 화면 진입,
읽음 처리와 끝까지 스크롤하는 시나리오를 각각 30회 측정한다.
