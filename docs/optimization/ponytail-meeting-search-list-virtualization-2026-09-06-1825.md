## 2. 변경 전

화면 전체가 `ScrollView`이고 검색 결과는 `map()`으로 그렸다. 결과 개수만큼 `MeetingListCard`를
첫 렌더에서 모두 만들기 때문에 목록이 길수록 초기 JS·네이티브 렌더 작업이 선형으로 늘었다.

```tsx
<ScrollView ref={meetingScrollRef} contentContainerStyle={styles.content}>
  {/* 모임 생성, 내 모임, 검색·필터 영역 */}
  <View style={styles.groupList}>
    {visibleDiscoverGroups.map((group) => (
      <View key={group.id}>
        <MeetingListCard {...group} />
      </View>
    ))}
  </View>
</ScrollView>
```

## 3. 가설·근거·기대 결과

### 가설

화면의 세로 `ScrollView`를 React Native 기본 `FlatList`로 바꾸고 검색 전 영역을 헤더로 옮기면,
결과가 긴 경우 화면 주변 카드만 먼저 만들어 초기 커밋 시간과 최악 프레임 간격이 줄어들고 기존
검색 결과의 ID·개수·순서와 상호작용은 유지될 것이다.

### 근거

- 코드 검색 결과 `visibleDiscoverGroups.map()` 한 곳에서 모든 카드를 즉시 생성했다.
- 같은 방향의 `ScrollView` 안에 `FlatList`를 중첩하면 가상화가 정상 동작하지 않으므로 기존 세로
  스크롤 컨테이너 자체를 교체했다.
- 이미 설치된 React Native의 `FlatList`와 `ListHeaderComponent`만 사용해 새 의존성이 필요 없다.
- 검색·추천 조회, 페이지 병합, 중복 제거, 오류 처리는 `useMeetingDiscover()`에 있어 렌더러 교체와
  분리돼 있다.

### 기대 결과와 성공 기준

| 지표 | 기준값 | 목표값 | 성공 조건 |
| --- | ---: | ---: | --- |
| 전체 행 즉시 생성 코드 | 1곳 | 0곳 | `map()` 렌더 제거 |
| 100·500개 250ms 행 생성 | N개 | N개 미만 | 화면 주변 행만 생성 |

| 결과 ID·개수·순서 | 기존 배열 | 동일 | 같은 배열과 키 사용 |
| API·상호작용 변경 | 0곳 | 0곳 | 대상 로직 diff 없음 |

### 근거

- 모든 검색 결과 카드를 즉시 만드는 `visibleDiscoverGroups.map()`이 1곳에서 0곳으로 줄었다.
- 기존 배열, `group.id` 키, 표시 순서, 카드 문구와 가입·방문 핸들러를 그대로 연결했다.

### 결론

모임 검색·추천 결과 목록을 React Native 기본 `FlatList`로 바꿔 전체 카드 즉시 생성 코드를
제거했고, 데이터·API·표시 순서·문구·가입 신청과 방문 로직은 유지했다. 핵심 변경은 98줄로
200줄 예산 안이며 새 의존성은 없다. Release 렌더러 실험에서 19개부터 첫 커밋이 35.5% 단축됐고,
100·500개에서는 각각 81.7%, 97.0% 단축됐다. 7개에서는 9.6% 느려져 가설은 목록 규모에 따라
부분 확인됐으며, 결과는 네트워크와 이미지 비용을 제외한 렌더러 마이크로 벤치마크로 한정한다.

### 후속 작업

실제 검색 결과가 20개 이상인 계정을 준비할 수 있을 때 실기기에서 검색 입력부터 첫 결과 표시와
목록 끝까지 스크롤하는 시나리오를 각각 30회 측정한다.
