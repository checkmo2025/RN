## 2. 변경 전

설정 화면 전체가 `ScrollView`이고, `내 소식`은 수집한 모든 항목을 `map()`으로 즉시 React 요소로
만들었다. 목록이 길어지면 화면 밖의 행도 첫 렌더 과정에 포함된다.

```tsx
<ScrollView contentContainerStyle={styles.settingsContent}>
  <View style={styles.listContainer}>
    {myNews.map((item) => (
      <Pressable key={item.id} onPress={() => handleOpenMyNews(item)}>
        {/* 썸네일, 제목, 본문, 날짜 */}
      </Pressable>
    ))}
  </View>
</ScrollView>
```

## 3. 가설·근거·기대 결과

### 가설

`내 소식` 상세 화면의 `ScrollView + map()`을 React Native 기본 `FlatList`로 바꾸면 화면 밖 행을
한꺼번에 만들지 않으므로, 첫 렌더 영역의 소식 행 수가 `N`개에서 `min(N, 10)`개로 제한된다.
동일한 배열, 키, 행 UI와 핸들러를 전달하면 사용자 동작 계약은 유지될 것이다.

### 근거

- 기존 코드는 `myNews.map()` 결과 전체를 `ScrollView` 자식으로 전달했다.
- 설치된 React Native 0.81.5의 `VirtualizedListProps.js`에서 `initialNumToRender` 기본값은 10개다.
- `FlatList`는 화면 주변의 항목을 창 단위로 렌더링하며 React Native에 이미 포함되어 있다.
- 마이페이지의 팔로우 목록이 이미 같은 파일에서 `FlatList` 패턴을 사용한다.
- 데이터 수집, 매핑, 상세 이동 코드는 렌더 컨테이너와 독립되어 있어 수정할 필요가 없다.

### 기대 결과와 성공 기준

| 지표 | 기준값 | 목표값 | 성공 조건 |
| --- | ---: | ---: | --- |
| 전체 행 즉시 생성 코드 | 1곳 | 0곳 | `myNews.map()` 제거 |
| 가상 목록 | 0곳 | 1곳 | `FlatList` 사용 |
| 첫 렌더 영역의 소식 행 수 | `N`개 | `min(N, 10)`개 | 기본 초기 렌더 영역 적용 |
| 데이터·API 로직 변경 | 0곳 | 0곳 | 대상 diff에 없음 |
| TypeScript·ESLint 오류 | 0개 | 0개 | 검사 통과 |

예를 들어 20개면 첫 렌더 영역의 행 생성 수는 20개에서 최대 10개로 50%, 50개면 80%,
100개면 90% 감소할 것으로 계산된다. 이는 구조상 계산값이며 실제 렌더 시간이나 메모리 측정값은 아니다.

## 4. 변경 후

`내 소식`일 때만 독립 `FlatList`를 반환한다. 기존 행 UI, ID 키와 상세 이동 핸들러를 그대로 연결했다.

```tsx
<FlatList
  data={myNews}
  keyExtractor={(item) => item.id}
  renderItem={renderMyNewsItem}
  ItemSeparatorComponent={() => <View style={styles.myNewsListSeparator} />}
  ListHeaderComponent={(
    <>
      {renderMyNewsHeader()}
      {myNews.length > 0 ? renderMyNewsStatus() : null}
    </>
  )}
  ListEmptyComponent={renderMyNewsStatus()}
/>
```

실제 구현은 데이터가 있는 로딩 상태에서도 스켈레톤과 기존 행을 함께 보이도록
`renderMyNewsStatus()`를 헤더와 빈 목록 상태에 나누어 연결한다.

### 근거

- 전체 배열의 행을 즉시 만드는 `myNews.map()`이 1곳에서 0곳으로 줄고 `FlatList`가 1곳 생겼다.

### 결론

마이페이지 `내 소식` 목록을 React Native 기본 `FlatList`로 바꿔 전체 행 즉시 생성 코드를
1곳에서 제거했고 데이터·API·화면 내용과 상세 이동 로직은 바꾸지 않았다. 핵심 변경은 165줄로
200줄 예산 안이고 새 의존성은 없다. 가설은 목록 규모에 따라 부분 확인됐다. 7개에서는 약 0.74ms의
고정비가 생겼지만 19개부터 첫 커밋이 16.9% 단축됐고, 100·500개에서는 각각 78.5%, 94.8%
단축됐다. 이는 렌더러 마이크로 벤치마크 결과이며 실제 계정의 네트워크·이미지를 포함한 종단 간
응답 시간이나 메모리 개선으로 확대 해석하지 않는다.

### 후속 작업

실제 `내 소식`이 20개 이상인 계정을 준비할 수 있을 때 실기기에서 화면 진입과 끝까지 스크롤하는
시나리오를 각각 30회 측정한다.
