## 2. 변경 전

검색 결과 전체를 세로 `ScrollView` 안에서 `map()`으로 즉시 만들었다. 한 페이지씩 결과가 추가될
때마다 이미 내려받은 카드 전부가 같은 비가상 목록에 포함되므로 결과가 길수록 첫 렌더 작업이 선형으로
늘어났다.

```tsx
<ScrollView onScroll={handleBottomDistance}>
  {/* 검색 입력, 결과 개수, 로딩·빈 상태 */}
  <View style={styles.resultList}>
    {searchResults.map((book, index) => (
      <Pressable
        key={`${book.isbn}-${index}`}
        onPress={() => handleSelectBook(book)}
      >
        {/* 표지, 제목, 저자, 설명, 좋아요, 책이야기 작성 */}
      </Pressable>
    ))}
  </View>
  {/* 추가 로딩·마지막 결과 */}
</ScrollView>
```

## 3. 가설·근거·기대 결과

### 가설

도서 검색 결과의 세로 `ScrollView`와 `searchResults.map()`을 React Native 기본 `FlatList`로 바꾸면
화면 주변 카드부터 만들기 때문에 긴 결과의 첫 커밋 시간, 초기 행 생성 수와 최악 프레임 간격이
줄어든다. 기존 배열, 키, 240px 추가 조회 조건과 카드 핸들러를 그대로 전달하면 사용자 동작 계약은
유지될 것이다.

### 근거

- 기존 `searchResults.map()`은 누적된 모든 결과 카드를 즉시 React 자식으로 만들었다.
- `FlatList`는 React Native에 포함돼 있어 패키지나 네이티브 설정을 추가하지 않는다.
- 검색 API, 캐시, 페이지 병합과 중복 제거는 `useBookSearch()`에 있어 목록 컨테이너와 분리돼 있다.
- 검색 결과와 도서 상세를 분리해 상세의 책이야기 `map()`과 표시 로직은 변경하지 않았다.

### 기대 결과와 성공 기준

| 지표 | 기준값 | 목표값 | 성공 조건 |
| --- | ---: | ---: | --- |
| 전체 결과 즉시 생성 코드 | 1곳 | 0곳 | `searchResults.map()` 제거 |
| 100·500개 250ms 행 생성 | N개 | N개 미만 | 화면 주변 카드만 생성 |
| 19·100·500개 첫 커밋 중앙값 | 변경 전 | 감소 | 같은 Release 조건 30회 비교 |
| 결과 ID·개수·순서 | 기존 배열 | 동일 | 같은 배열과 키 사용 |
| API·오류·권한 로직 변경 | 0곳 | 0곳 | 대상 로직 diff 없음 |

작은 목록에서는 `FlatList` 자체 고정비가 있을 수 있어 목록 크기별로 따로 판정한다.

## 4. 변경 후

```tsx
<FlatList
  data={searchResults}
  keyExtractor={(book, index) => `${book.isbn}-${index}`}
  ListHeaderComponent={/* 기존 검색 입력, 결과 개수, 로딩·빈 상태 */}
  renderItem={({ item: book }) => (
    <Pressable onPress={() => handleSelectBook(book)}>
      {/* 기존 표지, 제목, 저자, 설명, 좋아요, 책이야기 작성 */}
    </Pressable>
  )}
  ItemSeparatorComponent={() => <View style={{ height: spacing.xs }} />}
  ListFooterComponent={/* 기존 추가 로딩·마지막 결과 */}
  onScroll={({ nativeEvent }) => {
    const distanceToBottom =
      nativeEvent.contentSize.height -
      (nativeEvent.layoutMeasurement.height + nativeEvent.contentOffset.y);
    if (distanceToBottom <= 240) void loadMoreSearchResults();
  }}
/>
```

- 입력·결과 개수·스켈레톤은 `ListHeaderComponent`로, 추가 로딩·끝 문구는 `ListFooterComponent`로 옮겼다.
- 결과 카드의 내용과 선택·좋아요·작성 핸들러는 바꾸지 않았다.
- 상세 분기는 별도의 기존 `ScrollView`를 그대로 사용한다.

## 7. 가설 판단과 결론

### 판정

`부분 확인`

### 근거

- 모든 검색 결과 카드를 즉시 만드는 `searchResults.map()`이 1곳에서 0곳으로 줄고 `FlatList`가 1곳 생겼다.
- 기존 `searchResults`, 키, 순서, 카드 문구와 선택·좋아요·작성 핸들러를 그대로 연결했다.
- 검색 API, 캐시, 페이지 병합, 중복 제거, 오류와 권한 처리 코드는 수정하지 않았다.
- 19·100·500개에서 첫 커밋 중앙값이 각각 32.1%, 81.7%, 96.7% 줄었다.
- 100·500개에서 250ms 카드 생성이 40개로 제한되고 최대 프레임 간격 p95도 63.6%, 89.2% 줄었다.
- 7개에서는 첫 커밋 중앙값이 7.33ms에서 7.83ms로 6.9% 늘어 작은 목록의 고정비가 확인됐다.

### 결론

전역 헤더의 도서 검색 결과를 React Native 기본 `FlatList`로 바꿔 누적된 카드 전체를 즉시 만드는
구조를 제거했다. 데이터·API·표시 순서·문구·좋아요·작성·상세 이동은 유지했고 핵심 변경은 197줄로
200줄 예산 안이며 새 의존성은 없다. Release 렌더러 실험에서 19개부터 첫 커밋이 32.1% 단축됐고,
100·500개에서는 각각 81.7%, 96.7% 단축됐다. 7개에서는 6.9% 느려 가설은 목록 규모에 따라 부분
확인됐으며, 이 수치는 네트워크와 이미지 비용을 제외한 렌더러 마이크로 벤치마크로 한정한다.

시나리오를 30회 측정하면 API·이미지까지 포함한 사용자 체감 지표를 보완할 수 있다.
