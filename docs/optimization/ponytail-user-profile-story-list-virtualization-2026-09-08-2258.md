## 2. 변경 전

화면 전체가 `ScrollView`였고 `책 이야기` 탭은 `stories.map()`으로 화면 밖 카드를 포함한 전체
목록을 한 번에 React 자식으로 만들었다.

```tsx
const renderStoryCards = () => (
  <View style={[styles.gridContent, styles.cardWrap]}>
    {stories.map((story) => (
      <Pressable key={story.id} onPress={() => handleOpenStoryDetail(story)}>
        {/* 기존 이미지, 제목·요약, 좋아요·댓글 */}
      </Pressable>
    ))}
  </View>
);

<ScrollView refreshControl={/* 기존 새로고침 */}>
  {/* 프로필, 탭과 renderStoryCards() */}
</ScrollView>
```

## 3. 가설·근거·기대 결과

### 가설

기존 2열 카드 배열을 인접한 두 개씩 행으로 묶어 화면의 세로 컨테이너를 `FlatList`로 바꾸면
화면 주변 행부터 생성된다. 긴 목록의 첫 커밋 시간, 초기 카드 생성 수와 긴 프레임은 감소하고,
같은 `stories` 순서와 기존 카드 JSX·핸들러를 사용하므로 사용자 동작은 유지될 것이다.

### 근거

- 기존 `stories.map()`은 목록 크기와 관계없이 모든 카드를 첫 렌더에 생성했다.
- 화면은 2열이므로 인접한 원소 두 개를 한 행으로 묶으면 순서를 바꾸지 않고 하나의 세로 목록으로 가상화할 수 있다.
- React Native의 기존 `FlatList`만 사용하므로 새 패키지나 중첩 스크롤이 필요 없다.
- 조회·매핑·상세 이동 로직은 렌더 코드와 분리돼 있어 데이터 로직을 건드리지 않아도 된다.

### 기대 결과와 성공 기준

| 100·500개 250ms 카드 생성 | N개 | N개 미만 | 화면 주변 행만 생성 |

| 결과 ID·개수·순서 | 기존 배열 | 동일 | 인접한 두 항목만 한 행으로 묶음 |

### 근거

- 전체 카드를 즉시 만드는 렌더 영역의 `stories.map()`이 1곳에서 0곳으로 줄고 `FlatList`가 행을 받는다.

### 결론

다른 사용자 프로필의 `책 이야기` 2열 카드를 행 단위로 묶어 `FlatList`의 가상화 대상으로 옮겼다.
데이터·표시 순서·문구·상세 이동과 로딩·빈 상태는 유지했고 핵심 변경은 122줄로 200줄 예산의
61.0%이며 새 의존성은 없다. Release 실험에서 100·500개 첫 커밋은 각각 69.2%, 94.8%
단축됐지만 실제 15개에 가까운 19개는 6.4% 느려 현재 화면의 응답속도가 개선됐다고 볼 수 없다.
따라서 이번 변경은 프로필의 책 이야기가 많아질 때 초기 렌더 부하를 제한하는 확장성 개선이며
가설은 목록 규모에 따라 부분 확인으로 판정한다.
