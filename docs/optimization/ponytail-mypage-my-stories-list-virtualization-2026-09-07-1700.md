## 2. 변경 전

마이페이지의 바깥 `FlatList`는 `내 알림`에서만 데이터를 받았다. `내 책 이야기`는
`ListHeaderComponent` 안에서 `stories.map()`으로 모든 카드를 한 번에 만들었으므로 바깥 목록의
가상화 대상이 아니었다.

```tsx
const renderStories = () => (
  <View style={[styles.gridContent, styles.cardWrap]}>
    {/* 기존 로딩·빈 결과 */}
    {stories.map((item) => (
      <Pressable key={item.id} style={styles.storyCard}>
        {/* 기존 카드와 상세·임시저장 동작 */}
      </Pressable>
    ))}
  </View>
);

<FlatList
  data={isLoggedIn && activeTab === '내 알림' ? alarms : []}
  ListHeaderComponent={/* 프로필, 탭과 renderStories() */}
/>
```

## 3. 가설·근거·기대 결과

### 가설

기존 2열 카드 배열을 두 개씩 행으로 묶어 이미 존재하는 바깥 `FlatList`에 전달하면 화면 주변 행부터
생성된다. 긴 목록의 첫 커밋 시간, 초기 카드 생성 수와 긴 프레임은 감소하고, 같은 `stories` 순서와
기존 카드 JSX·핸들러를 그대로 사용하므로 사용자 동작은 유지될 것이다.

### 근거

- `stories.map()`은 화면 밖 카드를 포함한 전체 배열을 `ListHeaderComponent` 안에서 즉시 만들었다.
- 화면에는 두 열이 필요하므로 인접한 원소 두 개를 한 행으로 묶으면 카드 순서를 바꾸지 않고
  바깥 세로 `FlatList` 하나로 가상화할 수 있다.
- 기존 바깥 목록을 재사용하므로 중첩 가상 목록과 새 패키지가 필요 없다.
- 조회·매핑과 카드 이동·삭제 핸들러가 렌더 코드와 분리돼 있어 데이터 로직을 건드리지 않아도 된다.

### 기대 결과와 성공 기준

| 지표 | 기준값 | 목표값 | 성공 조건 |
| --- | ---: | ---: | --- |
| 전체 카드 즉시 생성 코드 | 1곳 | 0곳 | `stories.map()` 제거 |
| 100·500개 250ms 카드 생성 | N개 | N개 미만 | 화면 주변 행만 생성 |
| 100·500개 첫 커밋 중앙값 | 변경 전 | 감소 | 같은 Release 조건 30회 비교 |
| 결과 ID·개수·순서 | 기존 배열 | 동일 | 인접한 두 항목만 한 행으로 묶음 |
| API·상세·임시저장 로직 변경 | 0곳 | 0곳 | 대상 로직 diff 없음 |

## 4. 변경 후

```tsx
const storyRows = useMemo(
  () =>
    Array.from({ length: Math.ceil(stories.length / 2) }, (_, index) =>
      stories.slice(index * 2, index * 2 + 2),
    ),
  [stories],
);

const mainListItems =
  activeTab === '내 알림' ? alarms : activeTab === '내 책 이야기' ? storyRows : [];

<FlatList
  data={mainListItems}
  keyExtractor={(item) =>
    Array.isArray(item) ? `story-row-${item[0]?.id}` : item.id
  }
  renderItem={({ item }) =>
    Array.isArray(item) ? renderStoryRow(item) : renderAlarmItem(item)
  }
/>
```

- `renderStoryRow()`는 기존 카드 JSX와 상세·임시저장 분기를 그대로 사용한다.
- 로딩 스켈레톤과 빈 결과는 기존 헤더 영역에 남기고, 데이터가 있을 때만 행을 `FlatList`로 전달한다.
- 알림과 책 이야기 사이에서 같은 바깥 목록을 재사용해 중첩 스크롤을 만들지 않았다.

## 7. 가설 판단과 결론

### 판정

### 근거

- 전체 카드를 즉시 만드는 `stories.map()`이 1곳에서 0곳으로 줄고 기존 바깥 `FlatList`가 행을 받는다.
- 기존 `stories` 순서, 카드 JSX, 상세·임시저장 분기, 삭제 핸들러와 로딩·빈 상태를 유지했다.
- 조회 API, 데이터 매핑, 새로고침, 오류·로그인 로직은 수정하지 않았다.
- 100·500개에서 첫 커밋 중앙값이 각각 70.2%, 95.0% 줄고 20ms 초과 프레임은 33·47회에서 0회가 됐다.
- 19개에서는 첫 커밋 중앙값이 13.24ms에서 14.79ms로 11.7% 늘고 긴 프레임은 양쪽 모두 0회였다.
- 7개에서도 중앙값이 24.3% 늘어 작은 목록에서는 가상화 고정비가 확인됐다.

### 결론

마이페이지 `내 책 이야기`의 2열 카드를 행 단위로 묶어 기존 바깥 `FlatList`의 가상화 대상으로
옮겼다. 데이터·표시 순서·문구·상세 이동·임시저장 편집과 삭제는 유지했고 핵심 변경은 77줄로
200줄 예산의 38.5%이며 새 의존성은 없다. Release 실험에서 100·500개 첫 커밋은 각각 70.2%,
95.0% 단축되고 긴 프레임이 제거됐지만, 19개는 11.7% 느려 현재의 작은 목록에서 응답속도가
개선됐다고 볼 수 없다. 따라서 이번 변경은 현재 속도 향상보다 목록 증가 시 렌더 부하를 제한하는
확장성 개선이며 가설은 부분 확인으로 판정한다.

현재 실제 데이터 규모에서의 체감 비용을 보완할 수 있다.
