## 2. 변경 전

`ScrollView` 내부에서 배열 전체를 `map()`으로 즉시 React 요소로 만들었다. 목록이 길어질수록
현재 화면 밖에 있는 사용자 행도 함께 생성된다.

```tsx
<ScrollView refreshControl={refreshControl}>
  {activeFollowUsers.map((user) => (
    <View key={`${activeFollowTab}-${user.nickname}`} style={styles.followUserRow}>
      {/* 프로필과 팔로우 동작 */}
    </View>
  ))}
</ScrollView>
```

## 3. 가설·근거·기대 결과

### 가설

팔로우 페이지의 `ScrollView`와 `map()`을 React Native의 `FlatList`로 바꾸면 화면 밖 행을
한꺼번에 만들지 않으므로 긴 목록의 초기 렌더 작업과 메모리 사용을 줄일 수 있다. 동일한 데이터와
행 컴포넌트, 키, 상호작용을 전달하면 사용자 동작은 유지될 것이다.

### 근거

- `ScrollView`의 자식은 전체 배열을 `map()`하는 시점에 모두 생성된다.
- `FlatList`는 보이는 영역 주변의 항목을 창 단위로 렌더링하는 React Native 기본 컴포넌트다.
- 별도 라이브러리나 데이터 변환 없이 기존 배열을 `data`로 전달할 수 있다.
- 팔로우 페이지는 독립된 화면 분기라 상위 마이페이지의 책 이야기, 서재, 모임과 알림 목록을 건드리지 않는다.

## 7. 가설 판단과 결론

### 판정

`부분 확인`

### 근거

- 전체 배열의 행을 즉시 만드는 `map()`이 1곳에서 0곳으로 줄고 `FlatList`가 1곳 생겼다.
- 기존 `activeFollowUsers`, 닉네임 키, 버튼 핸들러와 새로고침 함수를 그대로 연결했다.
- 데이터가 있는 로딩 상태에서도 스켈레톤과 기존 행을 함께 표시하는 흐름을 유지했다.
- 정적 검사와 프로덕션 JS export는 통과했지만 런타임 성능과 화면 회귀는 측정하지 않았다.

### 결론

마이페이지의 팔로워·팔로잉 목록을 React Native 기본 `FlatList`로 바꿔 전체 행 즉시 생성 코드를
1곳에서 제거했다. 데이터, 순서, 프로필 이동, 삭제, 팔로우와 새로고침 로직은 그대로 연결했다.
핵심 변경은 188줄로 200줄 예산 안이며 새 의존성은 없다. 가상화 구조 적용은 확인했지만 실제
초기 렌더 시간, 프레임과 메모리 개선은 동일한 긴 목록의 변경 전·후 측정이 필요하다.
