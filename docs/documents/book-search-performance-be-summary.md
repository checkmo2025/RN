# 책 검색 성능 — 백엔드 공유용 요약

> 작성일: 2026-06-22 KST
> 대상: 백엔드팀
> 관련: RN 구현 계획/내역은 `docs/documents/book-search-latency-plan.md`

## 1. 결론
서버(알라딘 API) 성능은 손댈 수 없으므로 **RN(앱) 쪽에서 체감 지연을 줄였습니다.**
백엔드 추가 작업은 **필수 아님**. 아래 "협조하면 좋은 것"만 확인 부탁드립니다.

## 2. 측정 기반 (BE팀 제공 데이터)
- Redis **캐시 히트: 1~30ms** (매우 빠름)
- **캐시 미스(첫 알라딘 호출): 250~980ms** — 거의 전부 `aladinHttp`(알라딘 응답 대기)에서 발생. 변환/캐싱/likedByMe는 무시 수준.
- 즉 느린 건 **첫 검색(캐시 미스) 한 번**뿐, 이후는 서버가 빠름.

## 3. 앱(RN)에서 한 개선
공용 검색 훅 `useBookSearch`를 만들어 **헤더 · 책이야기 · 책장 3곳에 모두 적용**:
1. **타이핑 중 prefetch** — 입력 멈춤 400ms 후 백그라운드로 미리 검색 → **서버 Redis를 미리 데워둠**. 실제 "검색" 시점엔 이미 캐시 히트(1~30ms).
2. **클라이언트 캐시(TTL 3분)** — 같은 검색어 재검색은 서버 안 가고 즉시 표시.
3. **요청 낭비 차단** — 최소 2자 / 중복 검색어 제거 / 이전 요청 취소(AbortController) → 불필요한 알라딘 호출·트래픽 감소.

효과: 첫 검색을 제외하면 체감 거의 즉시. prefetch가 캐시를 미리 채워 **첫 검색 체감도 개선**.

## 4. 백엔드 협조 요청 (선택)
- **`/books/search`의 `totalResults`는 정상 수신되어 그대로 사용**(앱 "총 N개" 정확 표기 반영 완료). → **유지만** 부탁.
- (있으면 더 좋음) **캐시 미스를 더 줄이려면** 인기 검색어/베스트셀러를 **서버에서 주기적 prefetch(워밍)** 해두면, 앱 prefetch와 무관하게 첫 검색도 빨라짐. 여력 될 때 검토.

## 5. (참고) 연관 이슈 — 레이트리밋
- 별건이지만 **nginx IP 단위 레이트리밋**(`limit_req_zone $binary_remote_addr ... rate=10r/s`, `burst=20`, `limit_req_status 429`) 때문에 **같은 WiFi에서 단체(오프라인 독서모임 등) 동시 접속 시 429("요청이 많습니다")** 발생.
- 앱 prefetch는 debounce/최소자/중복제거로 요청을 최대한 줄였으나, 근본적으로 **IP 기준 제한을 사용자(토큰) 기준으로 변경하거나 한도 상향** 검토 부탁.
- 독서모임 앱 특성상 "같은 장소·같은 IP 다수 사용자"가 정상 상태라, 핵심 사용 시나리오에서 막히는 위험.

## 6. 한 줄 요약
앱에서 **prefetch + 캐시 + 요청 절감**으로 해결. 백엔드는 **`totalResults` 유지**만 필수이고, 여력 되면 **인기 검색어 서버 워밍**과 **레이트리밋 정책(IP→토큰)** 검토 권장.
